## 本次 develop 修改

Ubuntu 实测中的三个修复完整保留：`goal_handle` 避免 rclpy 属性冲突、目标使用最新 TF、地图足迹贴障后的短前视脱困。

本次只修正 `PathTracker` 的可见模式：

1. 脱困前视沿路径累计长度插值，计入当前位置到路径的接入段，最多 0.4 m；避免稀疏路径点将前视距离放大到数米。
2. 脱困与普通可见性统一使用地图原点的平移和旋转，处理浮点数落在栅格边界时的舍入误差。
3. 仅已处于保守足迹间隙内的姿态使用脱困；机器人中心位于障碍或未知单元时保持停车。
4. 检查到候选目标的连线：不得越出地图、穿过占用/未知单元，沿途插值后的地图距离估计不得低于起点。实时 LaserScan 的独立 safety 节点继续决定实际速度。

地图距离检查是栅格估计，不是物理无碰撞证明；新逻辑比 `40f2434` 更保守，无法找到符合条件的短目标时会报告 `no_visible_carrot`。需要重新定位或重新规划，不自动绕过安全节点。

修改没有改变训练环境、网络、奖励、BEV 契约或模型权重，因此本次不重训、不重新导出模型。已有 `linux_gazebo.json` 仍代表 `40f2434` 的实测。`40bc494` 的有界脱困已在虚拟机复测：多目标/reset 三段全部到点，reset 后仅出现 3 个 `tracking_escape` 采样（约 0.3 s）即恢复正常；运动中换目标 7.4 s 掉头到点；98 项测试与 C++/Python 一致性检查通过。记录见 `experiments/ppo_v2/verification/develop_linux_recheck.json`。

## 虚拟机使用 develop

先关闭旧 launch/Gazebo，保存虚拟机上的未提交修改。已有 develop 分支：

```bash
cd ~/ROS2hw
git switch develop
git pull --ff-only origin develop
bash training/scripts/build_ros_interfaces.sh
bash setup/run_ppo_home.sh
```

本机尚未建立 develop 分支时，先 `git fetch origin`，再 `git switch --track origin/develop`。依赖尚未准备好时，最后两条替换为 `bash setup/run_ppo_v2.sh`，它会安装依赖、编译、检查并启动。

继续使用 v1 对照时关闭当前 launch，运行：

```bash
bash setup/run_ppo_home.sh model_id:=split_mixed_pretrain_v1
```

这使用 develop 中保留的 v1 模型与固定前视，便于两种策略在同一套已修复的 ROS 基础设施上比较；main 分支没有因此改变。
