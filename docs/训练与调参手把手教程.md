# Windows 训练与调参手把手教程

## 1 先理解物理机负责什么

Windows 负责生成二维任务、训练 PPO、验证与测试策略、画曲线与轨迹、导出模型。Windows 不运行 ROS、SLAM、Nav2 或 Gazebo。你在 Windows 看见轨迹图，说明模型在二维环境中运行；只有虚拟机机器人受到 `/cmd_vel_rl` 驱动并完成任务，才能说明 Gazebo 策略部署成功。

项目都在 `E:\ROS2\project`，命令默认在 PowerShell 输入。无需激活环境，也不用输入裸 `python`；统一通过 `.\run.cmd`，避免误用你原有的 Python 3.11 或 3.12。

```powershell
cd E:\ROS2\project
.\run.cmd doctor
```

doctor 会打印 Python 版本、PyTorch/SB3/Gymnasium 版本、CPU、输入维度和 Gymnasium 检查结果。期望 Python 为项目内的 3.10，CUDA 为 false，32 格输入为 2056 维。实际电脑已有独立环境，第一次只需检查，不必重复下载依赖。

## 2 第一次应该怎样训练

本机实测后，推荐 `split_*32.yaml` 配置：先用小型 MLP 将 BEV 编码为 32 维，再直接拼接 8 个目标和运动标量，随后仍由 PPO 的 MlpPolicy 决策。它不改变消息和动作规格。原 `empty32.yaml`、`single32.yaml` 等保留为全量展平 MLP 的对照配置；两类特征提取器不能互相 resume。

如果你只是想接着本次已经训练好的模型做实验，不必重复下面的从零流程。可以先查看 `training/runs/split_mixed_100k_s42` 的结果，然后执行：

```powershell
.\run.cmd --config config\split_mixed32.yaml train --name my_mixed_continue_s42 --steps 300000 --seed 42 --resume training\runs\split_mixed_100k_s42\best_model.zip
```

先确认部署需要的传感器外参与足迹没有变化。上面的 seed 42 续训不构成新的独立训练种子。

### 第一步 先运行可复现的小检查

```powershell
cd E:\ROS2\project
.\python.cmd -m pytest training/tests/unit -q --basetemp=E:\ROS2\project\.tmp\pytest
.\run.cmd fixtures
```

测试失败时先修复，不开始长训。`fixtures` 产生给虚拟机 C++ 对照的标准输入，单独生成这些文件不等于 C++ 已通过验证。

### 第二步 先用空场景理解训练输出

```powershell
.\run.cmd --config config\split_empty32.yaml train --name my_empty_s42 --steps 10000 --seed 42 --eval-every 5000
```

名称对应 `training/runs/my_empty_s42`，已有同名目录会拒绝覆盖。重复实验换名称，例如 `my_empty_s42_v2`。`--steps 10000` 为请求步数，PPO 按完整 rollout 采样，实际步数可能稍大，以 `training_result.json` 为准。

先检查代码和日志能正常运行，短训成功率低不能直接说明 PPO 不适合。为了获得更充分的空场景模型，可另开 10 万至 30 万步实验：

```powershell
.\run.cmd --config config\split_empty32.yaml train --name empty_long_s42 --steps 300000 --seed 42
```

训练结束前不要关闭终端。需要中断时按一次 Ctrl+C，程序在可捕获中断时保存 `interrupted_model.zip`；该次运行没有 final_model 属于正常情况。强制关窗口或关机可能丢失最近进度，正式训练依靠周期 checkpoint。

### 第三步 看固定验证结果

```powershell
.\run.cmd evaluate --model training\runs\empty_long_s42\best_model.zip --split validation --episodes 12
.\run.cmd plot --run training\runs\empty_long_s42
```

打开运行目录中的 `learning_curves.png`，以及评估目录中的 `summary.json`、`episodes.csv`、`trajectories.png`。同一评估目录已经存在时需要使用新输出目录，防止覆盖：

```powershell
.\run.cmd evaluate --model training\runs\empty_long_s42\best_model.zip --split validation --episodes 12 --output training\runs\empty_long_s42\validation_v2
```

重点看成功次数、碰撞次数、失败原因和轨迹，不只看奖励。`mean_success_time=null` 表示没有成功样本，不能当作完成时间为零。

### 第四步 从简单障碍逐步加难

空场景达到可接受验证表现后，先进入单障碍：

```powershell
.\run.cmd --config config\split_single32.yaml train --name single_from_empty_s42 --steps 300000 --seed 42 --resume training\runs\empty_long_s42\best_model.zip
```

再训练转角或混合任务：

```powershell
.\run.cmd --config config\split_turn32.yaml train --name turn_from_single_s42 --steps 300000 --seed 42 --resume training\runs\single_from_empty_s42\best_model.zip
.\run.cmd --config config\split_mixed32.yaml train --name mixed_from_turn_s42 --steps 300000 --seed 42 --resume training\runs\turn_from_single_s42\best_model.zip
```

resume 表示从该模型继续增加给定步数，生成新目录并保存来源。阶段、任务距离或奖励变化会记录在新配置中。网络结构、BEV、传感器、运动和安全规格不一致时，脚本会拒绝直接续训，避免把不同输入含义混在同一模型中。

空场景预训练只是起点，不保证迁移到障碍后立即成功。也可在混合任务从头训练，与课程式训练形成两项独立实验，名称与日志要分开。

### 第五步 冻结方案再运行三个种子

先用种子 42 调试，在固定验证集确定方案后再运行正式三种子：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File training\scripts\train_three_seeds.ps1 -Stage mixed -Steps 300000 -Prefix formal_v1
```

它按 42、43、44 顺序训练，任一失败即停，不同时抢满 CPU。三个模型从头训练；如需每个种子独立完成课程式预训练，请分别按照第四步建立对应的三条训练链，不能把同一个空场景模型当作三个独立完整训练种子。

### 第六步 最后才使用测试集

```powershell
.\run.cmd evaluate --model training\runs\formal_v1_mixed_s42\best_model.zip --split test --episodes 24
```

训练时验证种子从 100000 开始，测试从 200000 开始，diagnostic 从 300000 开始。不同种子保证不同生成实例，不保证不同场景分布；真正未见布局或真实 Gazebo 家具环境仍需额外验证。看到测试失败后继续据此调参，该测试集就变成开发依据，应重新保留未使用的最终测试集。

## 3 如何看训练日志

| 输出 | 含义 | 建议关注 |
|---|---|---|
| `time/fps` | 训练整体吞吐 | 同配置比较性能，不能当成功率 |
| `rollout/ep_rew_mean` | 近期训练回报 | 曲线上升但仍需验证集到达 |
| `rollout/ep_len_mean` | 平均回合长度 | 变短可能是更快成功，也可能是更快碰撞 |
| `train/approx_kl` | PPO 策略更新幅度 | 激增时结合 clip_fraction 与实际退化判断 |
| `train/clip_fraction` | 被 PPO 裁剪的样本比例 | 长期很高可检查学习率和更新轮数 |
| `train/entropy_loss` | 探索相关量 | 要结合当前版本符号定义，不只看负值大小 |
| `task/reward_*` | 分项奖励累计 | 查清时间、间隙或转向项是否压过进度 |
| `validation/success_rate` | 固定验证任务成功率 | 模型选择的首要指标 |
| `validation/collision_rate` | 验证任务碰撞率 | 与安全干预共同看，不能只看零碰撞 |

开启 TensorBoard：

```powershell
.\python.cmd -m tensorboard.main --logdir E:\ROS2\project\runs --host 127.0.0.1 --port 6006
```

浏览器打开终端显示的本机地址。保持此终端运行，训练可在另一终端继续。端口被占用时换 6007。默认只监听本机，不开放局域网端口。

每次训练保存：`config.yaml`、`obs_spec.yaml`、`metadata.json`、`logs/progress.csv`、TensorBoard 事件、`validation_history.jsonl`、`best_validation.json`、best/final 模型。metadata 记录实际依赖、源码哈希与规格哈希，不要求先建立 Git 仓库。

## 4 修改前的固定流程

1. 复制当前配置，如 `config/mixed32.yaml` → `config/exp01.yaml`。
2. 在新文件中一次只改一类因素：奖励、PPO 参数或任务难度。
3. 使用新运行名，保持原配置、模型和数据。
4. 先做 1 万至 3 万步行为检查，确认没有实现错误，再投入长训。
5. 用相同验证任务、相同步数和相同种子对比，记录成功、碰撞、卡死与干预。
6. 确认有改善后再使用其他种子复验。

```powershell
Copy-Item config\split_mixed32.yaml config\exp01.yaml
notepad config\exp01.yaml
.\run.cmd --config config\exp01.yaml train --name exp01_s42 --steps 30000 --seed 42 --eval-every 10000
```

YAML 使用空格缩进，不能用 Tab。把 `0.01` 写成小数点形式，不用逗号；布尔值用 true/false。参数拼写错误可能导致无效或报错，改后先运行短命令验证。

## 5 训练不理想时具体改哪里

### 情况 A 机器人不动或一直原地转

先看 `episodes.csv` 中 reason 是 stuck、timeout 还是 collision，再看轨迹。零碰撞不等于会导航，安全模块可能一直帮它停车。

排查顺序：

1. `training/envs/navrl/control.py → scale_action`：检查线速度从 [-1,1] 映射到 [0,0.26]，a0=-1 才是停车；a0=0 是 0.13 m/s，不是停车。
2. `training/envs/navrl/control.py → filter_velocity`：看 intervention_duration 是否很高。若空房间也持续被拦截，查机器人半径、量程无效值和安全间隙。
3. `training/envs/navrl/env.py → _compute_reward`：比较 progress 和 time 的累计量。不能先凭感觉翻倍所有奖励。
4. `training/envs/navrl/env.py → _update_route`：确认子目标位于路线前方，没有跳到另一条交叉路线。
5. 若实现正确、探索不足，在实验 YAML 把 `ppo.ent_coef` 从 0.01 小幅提高到 0.02，做独立验证。探索增加可能提高碰撞，不能只看训练动作更活跃。

可尝试将 `reward.progress` 从 2.0 改为 3.0，或将 `reward.time` 从 -0.01 改为 -0.005，分别实验。不要增加每步无条件正的朝向奖励，否则朝向目标但原地不动也可能获利。

### 情况 B 直线会走，一遇障碍就撞或停车

1. 打开 `fixtures/front_wall.json`，对照 `training/envs/navrl/observation.py → rasterize`：x 正向对应列增加，不是数组行增加；训练和 RViz 显示的上下翻转不能改变模型输入。
2. 看 `training/envs/navrl/geometry.py → raycast` 的扫描范围、障碍几何和噪声，确认测距不是地图像素单位。
3. 看 `training/envs/navrl/env.py → _make_layout` 和 `reset`：是否从空场景突然跳到大量障碍，起终点距离是否过大。
4. 先用 single32，而不是立刻 mixed32。空场景只验证运动与目标跟随，没有训练足够避障行为。
5. 若碰撞前并无明显负反馈，比较 `reward.clearance` 与 `reward.collision`。可将 clearance 从 -0.02 改为 -0.03 单独验证，不能把间隙阈值放大到走廊宽度都无法通过。

关闭保护评估只能在二维仿真：

本次混合模型的 24 次另外生成任务中，5 次失败均为 stuck；同 12 个验证任务开启保护时 0 次碰撞，关闭后 3 次碰撞，成功数仍为 9。这类情况应先检查 `filter_velocity` 的拦截原因、局部目标是否跨过转角，以及策略能否主动改变路线。单纯放松安全间隙可能只是把卡死变成碰撞，不等于策略变好。相关数据在 `training/runs/split_mixed_100k_s42/validation_safe_12` 和 `validation_unfiltered_12`。

```powershell
.\run.cmd evaluate --model training\runs\mixed_from_turn_s42\best_model.zip --split validation --episodes 12 --no-safety --output training\runs\mixed_from_turn_s42\ablation_no_safety
```

与同模型同任务的安全开启评估配对分析。这个消融回答部署保护的影响，不证明无保护策略经过了独立训练。

### 情况 C 空场景好，转角失败

检查 `training/envs/navrl/env.py → _update_route` 的前视距离和 `training/envs/navrl/geometry.py → plan_path` 的路径与障碍膨胀。前视过远可能使局部目标跨越拐角，策略需要学会绕行；简单目标跟随器也可能因此卡住。

在实验 YAML 中把 `environment.lookahead` 从 1.2 改为 0.8 或 1.0，仍需在训练和 ROS 端保持一致并记录新实验。它不改变输入维度，但会改变任务语义，应重新验证。

如果训练奖励在绕行时连续负值，确认使用的是同一路径弧长进展，而不是到最终目标欧氏距离。实现位置是 `_update_route` 与 `_compute_reward`。本项目不在线重规划；加入重规划时必须在更新路径后重置进度基准，避免突然获得进度奖励。

### 情况 D 奖励升高但成功率不升

到 `training/envs/navrl/env.py → _compute_reward` 检查是否在刷某个奖励，随后看 `step` 的 success、collision、hold 与超时判定。

必须确认 success 只在距最终目标 0.3 m 内保持 1 秒且没有碰撞时成立。局部子目标不等于最终成功。训练日志里回合变短可能来自碰撞，不代表到达更快。

模型选择在 `training/scripts/run.py → ValidationCallback.validate`。默认按成功率优先，其次更低碰撞率，再平均回报，不按训练奖励最大直接挑模型。若你更改选择规则，请写进报告并在正式测试前冻结。

### 情况 E 经常超时

先算理论时间：8 m / 0.26 m/s 约 30.8 秒，还未计算转向和绕行。`training/envs/navrl/env.py → reset` 根据参考路径生成不短于基础预算的回合上限。

在 YAML 中看 `environment.max_steps`、`timeout_factor`、`goal_hold_seconds`。不能仅为某个方法失败而单独加时。调整回合上限时保留统一任务清单和超时规则。

若几乎原地转到超时，回到情况 A；若安全过滤持续停车，回到情况 B；不是所有超时都应增加 max_steps。

### 情况 F 训练突然不稳定或越训越差

1. 先使用 best_model 对照 final_model 的固定验证结果。
2. 新实验把 `ppo.learning_rate` 从 3e-4 降到 1e-4。
3. 若更新轮数过多，再单独把 `ppo.n_epochs` 从 10 改为 5。
4. 查看 approx_kl、clip_fraction、value_loss 是否与行为退化同步。
5. 固定种子与评估任务，不同时改变奖励和课程难度后再推断学习率的作用。

继续训练示例：

```powershell
.\run.cmd --config config\exp01.yaml train --name exp01_continue --steps 100000 --seed 42 --resume training\runs\exp01_s42\best_model.zip
```

训练代码会采用当前 YAML 的学习率、熵系数、rollout 大小、batch_size、更新轮数及折扣参数；网络结构仍必须一致。继续训练后奖励量表变化时，不直接比较新旧回报绝对值，优先比较任务指标。

本次实测的排查例子：展平 MLP 在空场景固定验证上最高 4/8，采用 split_mlp 后固定验证达到 8/8，24 个另外生成的空场景任务成功 23 个。两次运行的并行设置和训练轨迹也不同，这只是选择候选实现的工程依据，不能写成严格控制变量后证明了特征融合的因果效果。若要将其作为报告消融，应统一训练预算、环境数、种子与数据分布重新对照。

### 情况 G 模型太慢

先实测，关闭占资源的虚拟机任务后执行：

```powershell
.\run.cmd benchmark --steps 10000 --envs 1 2 4 --vec-env dummy
.\run.cmd benchmark --steps 10000 --envs 1 2 4 --vec-env subproc
```

结果保存在 reports。sample_fps 只含采样，ppo_fps 包含策略采样与训练更新，不能拿两者直接当加速倍数。多进程包含额外启动成本，第一次 JIT 编译与磁盘缓存也会影响结果。

在配置中调整 `training.n_envs`、`vec_env`、`torch_threads`，先试 1、2、4 环境和 1、2、4 线程，不因 CPU 有 28 个逻辑线程就全部开满。`batch_size` 必须整除 `n_envs*n_steps`。

`training/envs/navrl/geometry.py → raycast` 和 `training/envs/navrl/observation.py → rasterize` 是采样计算主要位置，已用 Numba 编译。首次运行编译慢不代表长期吞吐；不要轻易去掉缓存或每次清理它。

### 情况 H 想从 32 格升到 48 格

```powershell
.\run.cmd --config config\formal48.yaml train --name formal48_s42 --steps 300000 --seed 42
```

不要加旧 32 格模型的 `--resume`。32 和 48 格都覆盖 4.8 m，输入分别是 2056、4616 维，模型第一层参数不同。必须重新训练、重新生成对应样例、重新导出并在虚拟机重新检查。

只把 32 改成 48 不保证更好。高分辨率输入变大，MLP 的数据需求可能增加；比较时统一步数、场景和种子，并同时记录吞吐与成功率。

### 情况 I 想改策略网络或算法

当前策略在 `training/scripts/run.py → make_model`：`PPO('MlpPolicy', ...)`。隐藏层在配置 `ppo.net_arch: [128, 128]`。

`ppo.feature_extractor` 可以是 `flat` 或 `split_mlp`。flat 将整张 BEV 与状态一起输入策略网络；split_mlp 在 `training/envs/navrl/features.py → BevStateExtractor.forward` 中先编码 BEV，再拼接目标与运动状态。后者针对大量栅格输入可能使少量目标标量难以被利用的问题，已在本机空场景试训中观察到改善，但仍需障碍场景和其他种子验证。更改提取器需要从头训练，不复用原 flat 权重。

先考虑任务与接口，再做 `[64,64]` 或 `[256,128]` 的独立实验。网络形状变化从头训练，不续接旧权重。当前输入是展平的 BEV 和 8 个标量，不能仅把 MlpPolicy 字符串改为 CnnPolicy 就当作成功切换；那需要重新设计 Dict 观测或特征提取器、图像范围和模型导出接口。

本项目连续速度控制使用 PPO。DQN 需要离散动作空间，不能直接替换类名；SAC 等算法也有不同采样与更新配置。在当前课程目标下，优先完成现有 PPO 闭环，再把算法对比作为独立拓展。

### 情况 J Windows 很好，Gazebo 很差

先不要加训练步数，按以下顺序排查：

1. 导出包 `deployment/verify_bundle.py`：核对模型哈希及固定观测推理。
2. `training/scripts/check_fixture_outputs.py`：核对真实 C++ 输出与 Python 参考。
3. 核对扫描束角度、雷达平面外参、未知值、数组 C/H/W 顺序、机器人足迹和时间戳。
4. 核对目标四维、速度四维的归一化，没有再除以 255。
5. 核对 policy_node 输出只是目标速度，安全节点执行速率限制后反馈的是实际执行动作。
6. 检查实际控制频率和 Gazebo 延迟，确认不是训练 0.1 秒、部署 0.2 秒。
7. 观测与动作一致后，再在训练中逐项增加传感噪声、延迟或足迹变化，并用真实失败案例设计新训练布局。

两个仿真器的差异仍然存在；通过固定输入检查只说明实现相符，不等于已经验证迁移效果。

## 6 哪些改动需要重新训练

| 修改 | 能否直接用旧模型 |
|---|---|
| 日志、绘图、评估输出路径 | 可以，指标口径保持一致 |
| 学习率、更新轮数、熵系数 | 可以新实验续训并记录 |
| 奖励、课程难度、前视距离 | 可作为新实验续训，必须重新评估 |
| BEV 尺寸、通道、排列、目标或速度含义 | 不可以，重新训练 |
| 线速度或角速度缩放、dt、雷达外参、足迹 | 当前脚本拒绝跨规格续训，应重新训练 |
| 网络隐藏层形状 | 不可以，重新建立模型 |
| MLP 换 CNN、PPO 换其他算法 | 需要改观测或训练结构，独立实验 |

## 7 如何记录一次调参

复制下面模板，保存到 `docs/调参记录.md`。一次只记录一项实验，不用“感觉变好”替代结果。

```text
实验名称：
基线模型和配置：
修改的文件和字段：
修改原因与预期行为：
训练种子和实际步数：
验证任务与样本数：
成功数 / 总数：
碰撞数 / 总数：
主要失败原因：
安全干预时长：
典型轨迹文件：
是否保留及原因：
```

课程答辩可重点解释一次具体失败如何定位到观测、奖励或动作函数，以及修改后在同样验证条件下发生了什么。即使 PPO 没有全面优于 Nav2，真实、可复现的失败分析仍比只展示成功视频更有说服力。
