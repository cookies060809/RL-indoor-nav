## 1. 项目目标与实施原则

### 1.1 总体路线

在课程机器人仿真平台上完成室内自主导航：建图、地图保存与加载、定位、全局路径规划、局部避障和实验评价。

总体路线保持为：

> **传统导航提供定位与全局路径，BEV 与 PPO 承担局部决策，独立安全节点负责最终速度输出。**

项目贡献定位为：适配本机资源的系统实现、训练与部署接口的一致性、可复现的对照实验；不把 BEV、PPO、Nav2 本身当作原创算法。

### 1.2 必须完成的成果

- Gazebo 中机器人可运动，激光、里程计、TF 和仿真时钟正常。
- 使用 slam_toolbox 完成建图，保存地图，并在重新启动后加载地图导航。
- Nav2 完成多组起终点导航，作为传统方法基线。
- 自定义 C++ 节点把激光观测转换为局部 BEV，并在 RViz 中显示。
- 自行实现二维训练环境，用 PPO 训练策略，保存模型、配置、日志和评估结果。
- Python 推理节点加载模型，在 Gazebo 中完成局部导航闭环。
- 独立安全节点统一输出速度，支持急停、超时停车、模式切换和干预记录。
- 完成 Nav2 与 PPO 对照实验，提交可追溯的数据、报告、源码、截图和视频。

### 1.3 核心完成后再增加

优先增加：安全机制消融、未见布局测试。

动态障碍、虚拟同行者属于拓展，不影响基础交付；不扩展到三维感知、四足控制或大型视觉网络。

### 1.4 验收原则

- 每个阶段必须留下可检查的产物，才能进入下一阶段。
- 文中的成功率门槛是内部工程目标，不是教师评分，也不代表已经实现。
- 最终报告只填写真实实验数据，失败样本不删除。
- 计划中的事项只有在产物存在并验证后才算完成。

### 1.5 为本地运行做的六个调整

| 调整 | 原设想 | 本地方案 | 原因 |

## 3. ROS 2 与仿真平台最小概念

### 3.1 工作空间、功能包、节点

```text
~/ros2_ws/                 ROS 2 工作空间
├── src/                   源码
├── build/                 编译中间文件
├── install/               编译产物（需要 source）
└── log/                   编译日志
```

- 功能包（package）：独立功能单元，例如 `bev_pkg`。
- 节点（node）：运行中的程序。
- 编译：`colcon build`。
- 让终端认识包：`source install/setup.bash`。

```bash
cd ~/ros2_ws
colcon build --symlink-install
source install/setup.bash

ros2 pkg list
ros2 run <包名> <可执行名>
ros2 launch <包名> <launch文件>
```

### 3.2 话题、消息、服务、动作、参数

| 概念 | 方向 | 项目例子 | 说明 |
|---|---|---|---|
| 话题 Topic | 发布/订阅，异步 | `/scan`、`/cmd_vel` | 传感器和控制指令 |
| 消息 Message | 数据类型 | `sensor_msgs/msg/LaserScan` | 话题里的数据格式 |
| 服务 Service | 请求/响应 | 保存地图、复位 | 一问一答 |
| 动作 Action | 长任务 + 反馈 | `ComputePathToPose` | 可查询进度、可取消 |
| 参数 Parameter | 配置 | BEV 分辨率、速度上限 | 节点启动时读取 |

```bash
ros2 topic list
ros2 topic echo /scan --once
ros2 topic hz /scan
ros2 node list
ros2 interface show sensor_msgs/msg/LaserScan
```

### 3.3 TF2 坐标变换

本项目坐标链：

```text
map ──> odom ──> base_footprint ──> base_link ──> laser_link
 │        │            │                              │
 │        │            └─ 机器人地面基准点              └─ 激光雷达
 │        └─ 里程计坐标系
 └─ 地图坐标系
```

- 建图时：slam_toolbox 发布 `map → odom`。
- 已知地图导航时：AMCL 发布 `map → odom`。
- **两者不能同时运行并竞争同一变换。**
- Gazebo 平面运动插件发布 `odom → base_footprint`，20 Hz。
- `base_footprint → laser_link` 是静态变换。

```bash
ros2 run tf2_ros tf2_echo odom base_footprint
ros2 run tf2_ros tf2_echo map base_footprint
ros2 run tf2_tools view_frames
```

### 3.4 Gazebo Classic 在做什么

Gazebo 负责三件事：物理、传感器、世界。

- `gzserver`：物理和传感器，无界面，实验时只跑它。
- `gzclient`：三维显示，截图/录视频时再开。

课程机器人 `wpb_home` 的实测参数：

| 项目 | 数值 |
|---|---|
| 激光雷达 | 360 线，360°，10 Hz，0.24–10 m，噪声 σ=0.01 m |
| 雷达坐标系 | `laser_link`，`base_link` 上方 0.15 m，传感器再偏移 0.06 m |
| 里程计 | 20 Hz，`odom → base_footprint` |
| IMU | 100 Hz，`/imu/data` |
| 机器人半径 | 约 0.22 m（Nav2 参数），几何体约 0.226 m |
| Nav2 默认限速 | 0.26 m/s，1.0 rad/s |
| 底盘运动 | `libgazebo_ros_planar_move`，速度直接驱动 |

机器人半径只能作为初始近似，碰撞和间隙计算必须以实际足迹为准。

### 3.5 Nav2、SLAM、RViz、rosbag

| 工具 | 作用 |
|---|---|
| Nav2 | 定位、全局规划、局部控制、恢复行为 |
| slam_toolbox | 激光 SLAM 建图 |
| RViz2 | 可视化；设置初始位姿和目标 |
| rosbag2 | 记录/回放话题 |

Nav2 组件：

- `map_server`：加载地图。
- `AMCL`：已知地图定位，发布 `map → odom`。
- `planner_server`：全局规划，本项目使用 NavFn，发布 `/plan`。
- `controller_server`：局部控制，本项目使用 DWB；节点默认话题是 `/cmd_vel`，在 Nav2 bringup 中通常重映射为 `/cmd_vel_nav`。
- `bt_navigator`：行为树调度。
- `behavior_server`：恢复行为。

### 3.6 仿真时间与实时率

- 所有节点统一 `use_sim_time: True`。
- 实时率（RTF）小于 1 时，仿真时间比墙钟慢；`ros2 topic hz` 看到的是墙钟频率，低于设定值是正常现象。
- 低实时率不能直接当作通信故障。

### 3.7 最小数据流

```text
Gazebo 雷达 ──/scan──> 你的节点 ──/cmd_vel──> Gazebo 底盘
      │                                      │
      └──────────/clock、/tf──────────────────┘
```

课程第 8 章的避障程序就是这个结构。本项目的 RL 局部导航只是把“计算速度”的部分换成神经网络，接口不变。

## 4. 系统架构与控制权限

### 4.1 共用基础模块

两种模式共用：机器人模型、激光、地图、AMCL、全局规划器、安全输出。

所有 ROS 节点启用 `use_sim_time`。传感器处理使用消息时间戳查询 TF，不用最新 TF 无条件替代历史观测的变换。激光订阅匹配传感器 QoS，静态地图与静态 TF 按发布端持久性设置订阅。

### 4.2 Nav2 模式（基线）

```text
Gazebo → 激光与里程计 → AMCL
地图与目标 → Nav2 全局规划 + DWB
           → controller_server → /cmd_vel_nav
           → velocity_smoother（可选，需处理输出话题）
           → safety_node → /cmd_vel → Gazebo 底盘
```

必须检查：

- `controller_server`、`behavior_server`、`velocity_smoother` 是否启动。
- 课程包原有底盘节点的订阅关系。
- Nav2 内部原始速度、平滑后速度和最终速度的实际话题。
- 最终输出统一进入 safety_node，不能只加一条全局重映射就认定正确。

本课程包的 `nav2_bringup` 默认启动 `velocity_smoother`：`controller_server` 的 `cmd_vel` 输出已被重映射为 `/cmd_vel_nav`，`velocity_smoother` 平滑后再发布为 `/cmd_vel`。因此标准 Nav2 的最终输出是 `velocity_smoother` 的 `/cmd_vel`，不处理就会和 `safety_node` 争抢 `/cmd_vel`。

推荐两种做法：

- **A：保留 velocity_smoother**。复制并修改 Nav2 的 navigation launch，把 `cmd_vel_smoothed` 重映射为 `/cmd_vel_nav_smoothed`；`safety_node` 订阅它并输出 `/cmd_vel`。
- **B：移除 velocity_smoother**。在自定义 launch 中不启动平滑器，让 `controller_server` 的 `/cmd_vel_nav` 直接进入 `safety_node`，由安全节点统一做限速和速率限制。

无论哪种，都用 `ros2 topic info /cmd_vel --verbose` 和 `ros2 node info <节点>` 验证实际连接，不能只看 launch 文件。

### 4.3 PPO 模式（核心）

```text
地图与最终目标 → route_manager → ComputePathToPose Action
                               ↓ 返回全局路径
激光与 TF → bev_node      全局路径 → local_goal_node
                  ↓                ↓
                  带时间戳的策略观测 PolicyObservation
                           ↓
                     policy_node
                           ↓ /cmd_vel_rl
                     safety_node
                           ↓ /cmd_vel
                       Gazebo 底盘
```

关键设计：

- `route_manager` 主动调用 Nav2 的 `ComputePathToPose` Action，接收并保存返回的 `nav_msgs/Path`，发布 `/global_path`。
- 不依赖完整导航任务顺带发布的 `/plan`，也不同时发送会启动传统控制链的 `NavigateToPose`。
- RL 模式可以只启动地图、定位、规划器、全局代价地图和生命周期管理组件。
- 如果初期保留完整 Nav2，必须取消已有导航动作、阻断其底盘控制权限，并验证恢复行为不会介入。

查看 Action：

```bash
ros2 action list | grep compute_path
ros2 action info /compute_path_to_pose
```

### 4.4 规划与子目标更新

- 收到新目标后立即请求规划。
- 初始重规划周期 2 秒；偏离路径超过 0.5 m、持续无进展或目标改变时也触发。
- 规划请求只允许一个在途实例，丢弃被新目标替代的旧结果。
- 规划失败且旧路径仍有效时，可在预设短期限内保留旧路径；没有有效路径时停车并报告失败。
- 超过路径有效期限后停车。

子目标：

- 以机器人在路径上的投影为起点。
- 沿路径弧长前视 1.0–1.5 m。
- 最近点搜索约束在历史进度附近，避免折返路线或路径交叉处跳到另一段。
- 新路径到达后重新建立进度关联。
- 接近终点时直接使用最终位置。

### 4.5 模式状态与唯一速度出口

模式：`stop`、`nav`、`rl`，启动默认 `stop`。

- 模式请求与实际模式状态分开发布。
- 切换时先撤销当前任务并发零速度，清空候选命令、历史动作和路径状态，再启用新来源。
- 新来源数据未就绪时保持停车。
- `/cmd_vel` 只能由 `safety_node` 发布；遥控、Nav2、PPO 都不能绕过它。

验证：

```bash
ros2 topic info /cmd_vel --verbose
```

在模式切换、恢复行为启动、遥控退出时重复检查。

| `/local_goal` | `geometry_msgs/PoseStamped` | 明确坐标系与时间戳 |
| `/policy_observation` | `project_msgs/PolicyObservation` | 同步后的策略输入 |
| `/bev_grid` | `nav_msgs/OccupancyGrid` | 0=空闲，100=占用，-1=未知 |
| `/cmd_vel_nav` | `geometry_msgs/Twist` | Nav2 候选命令（原始或按 launch 约定） |
| `/cmd_vel_nav_smoothed` | `geometry_msgs/Twist` | 保留 velocity_smoother 时的平滑输出 |
| `/cmd_vel_rl` | `geometry_msgs/Twist` | PPO 候选命令，目标 10 Hz |
| `/cmd_vel` | `geometry_msgs/Twist` | 唯一底盘输入，安全节点约 20 Hz 输出 |
| `/estop_request` | `std_msgs/Bool` | true 锁存急停，false 不自动解除 |
| `/estop_state` | `std_msgs/Bool` | 当前急停状态 |
| `/safety/reset` | `std_srvs/Trigger` | 条件正常时显式复位 |

### 4.8 PolicyObservation 设计

把 BEV、局部目标、运动状态放进**同一条消息**，避免分开订阅时拼到不同时间的数据。

建议消息：

```text
std_msgs/Header header
string spec_version
uint16 height
uint16 width
float32 resolution
float32[] bev          # C×H×W，通道优先
float32[4] goal        # dx/d, dy/d, clip(d/5,0,1), atan2(dy,dx)/π
float32[4] motion      # v/0.26, ω/1.0, prev_v, prev_ω
```

规则：

- `header` 表示激光观测时刻。
- 目标和位姿转换到该时刻的机器人坐标系。
- 过旧或不可变换的数据不进入推理。
- BEV 数组排列、通道顺序、归一化规则必须与训练端完全一致。

### 4.9 急停、状态与复位

- `/estop_request` 与 `/estop_state` 严格分离，避免把反馈状态当控制请求循环使用。
- 急停请求 true 时锁存，false 不自动解除。
- 只有条件正常且收到 `/safety/reset` 才复位。
- 安全状态包含模式、命令来源、输入是否过期、减速/停车原因、原始速度与执行速度。

## 5. BEV 与策略输入规格

### 5.1 冻结一套正式规格

正式目标为 48×48×2；32×32×2 用于早期性能验证。两者都覆盖 4.8 m × 4.8 m：

- 48 格：0.10 m/格
- 32 格：0.15 m/格

这样比较输入规模时不会同时缩小感知范围。更改尺寸必须重新训练，旧模型不能用于新形状。

| 字段 | 约定 |
|---|---|
| 机器人坐标 | `base_footprint`，x 向前，y 向左 |
| 局部范围 | x、y 均为 [-2.4, 2.4) m |
| 栅格索引 | `col=floor((x+2.4)/resolution)`，`row=floor((y+2.4)/resolution)` |
| 通道 0 | 空闲 0，占用 1，未知 0.5 |
| 通道 1 | 到占用或未知格的欧氏距离，截断 1 m 后归一化 |
| 数组排列 | C×H×W；W 对应 x，H 对应 y |
| 目标向量 | `dx/d, dy/d, clip(d/5,0,1), atan2(dy,dx)/π` |
| 运动状态 | `v/0.26, ω/1.0`，以及上一周期实际执行的 `v, ω` 归一化值 |

- 目标距离 d 接近零时，方向分量置零，避免除零。
- 正式输入维度：`48×48×2 + 8 = 4616`。
- 32 格版本：`32×32×2 + 8 = 2056`。
- 未知格在距离层中按障碍处理（保守）；占用通道仍保留未知编码。
- 单帧 BEV 不含障碍物速度，基础项目只针对静态障碍，不能声称已解决动态避障。

### 5.2 激光转栅格

1. 按激光消息时间戳查询 `laser_link → base_footprint` 的完整 TF。射线从实际雷达原点出发，不默认从机器人中心出发。
2. 栅格初始化为未知。合法有限回波沿射线清空空闲格，只有确实位于局部范围内的命中端点才标记占用。
3. 按传感器插件语义处理无回波：
   - `+inf` 表示量程内无命中时，清空至最大有效距离或栅格边界，不制造障碍端点。
   - `NaN`、低于最小量程或其他无效读数不提供空闲证据。
4. 超过局部范围的合法回波，其射线仍清空经过的局部格，边界不标记为障碍。用射线与方形区域交点裁剪，不能用固定半径代替方形边界。
5. 同一帧冲突时，占用证据优先。机器人内部已知区域按模型足迹处理；近距离回波不能全部当作自身删除。
6. 用**欧氏距离变换**生成距离层，两端使用相同算法和截断规则，不用四邻域 BFS 的曼哈顿距离。

初期只做单帧重建，不做跨帧累积。未知格保守参与距离层，同时保留占用通道中的未知编码。若射线稀疏导致未知过多，通过分辨率和观测模型修正，不能在部署端单独把未知改为空闲。

### 5.3 一致性验收必须先于正式训练

固定输入样例至少覆盖：

- 空场景无回波
- 前墙
- 左右障碍
- 转角
- 边界端点
- NaN
- 最小量程
- 雷达非零平面偏移
- 目标接近零

向 Python 训练观测函数与 C++ 节点输入等价的 scan、TF、目标和运动状态。验收要求：

- 占用层逐格一致。
- 距离层和标量在浮点容差内一致，初始容差 `1e-5`。
- 目标在左侧时 `dy` 为正，前方障碍出现在 x 正方向。
- 动作缩放、限幅、速率限制一致。
- 失败时输出差异位置和可视化，不只比较数组形状。

然后用同一固定观测在 Windows 和 Ubuntu 加载模型，比较确定性动作输出。保存样例、结果和规格哈希；任一端修改观测定义后重新执行。

Gazebo 与二维环境无法保证逐帧相同；以上验收验证的是**等价输入下的接口实现**。

### 5.4 性能预算

- BEV 构建与推理目标 10 Hz。
- 观测处理 + 推理 p95 目标 < 100 ms。
- 不满足时先优化或统一降频，再重新验证训练与部署动作周期。

## 6. 二维训练环境与 PPO

### 6.1 运动与动作定义

采用平面独轮车约束，禁止侧向速度和倒车。若课程底盘允许全向运动，两种实验方法都统一设置 `vy=0`。

```text
动作 a0、a1 ∈ [-1, 1]
v_target = (a0 + 1) / 2 × 0.26 m/s
ω_target = a1 × 1.0 rad/s
控制周期 dt = 0.1 s
初始加速度上限：0.5 m/s²、2.0 rad/s²
```

- 速率限制按实际 dt 计算，10 Hz 和 20 Hz 节点不能直接使用同一个每步增量。
- 训练端模拟限速、加减速和实际执行动作反馈。
- 部署端记录安全模块修改后的速度。
- 舒适减速与紧急制动分开配置，紧急停车不受平滑限制。
- 位姿积分、激光生成、碰撞几何统一使用米和弧度。
- 碰撞检测使用足迹与障碍几何相交，不通过雷达最小量程推断碰撞。

### 6.2 训练任务与局部目标

- 先程序化生成矩形房间和障碍物。
- 起终点必须在可通行区域且有有效路径；不可达样本不能当作策略失败。
- 训练端也生成参考路径，并使用与部署一致的前视子目标逻辑。
- 初期：空场景、单障碍；之后：转角、窄通道、随机布局。
- 训练、验证、测试地图使用分开的布局和种子清单。
- Gazebo 测试场景不能反复用于选模型后仍称为未见场景。

### 6.3 回合长度与终止

- 初期局部任务 400–600 步，即 40–60 秒，再按路径长度校准。
- 正式 Gazebo 任务独立超时：

```text
T_limit = max(90 s, 3 × L_reference / 0.26 + 15 s)
```

`L_reference` 是同一起终点的固定参考路径长度。每组任务的超时在测试前冻结，两种方法一致。

- 碰撞和成功属于任务终止；时间上限属于截断。正确设置 Gymnasium 的 `terminated` 与 `truncated`。
- 连续 10 秒沿路径进展不足 0.05 m 作为卡死候选，结合转向/恢复状态核验；不因正常原地转向立即判失败。
- 基础任务以位置到达为目标：距最终点 0.3 m 内保持 1 秒且无碰撞即成功。
- 局部目标的方向误差不等同于最终姿态要求；若增加目标朝向，需单独定义并让两种方法同时启用。

### 6.4 奖励函数

先使用可解释的少量奖励项：

```text
r = 2.0 × Δs
    - 0.01
    - 0.02 × max(0, (0.20 - clearance) / 0.20)
    - 0.005 × abs(ω_t - ω_(t-1))
成功额外 +20，碰撞额外 -20
```

- `Δs` 是同一参考路径上的前进距离，不是欧氏距离；路径更新时重新建立进度基准。
- `clearance` 是足迹到障碍的外部间隙，单位米。
- 初期不设置持续朝向奖励，避免机器人不移动也能长期得正收益。
- 不用过大的绝对角速度惩罚抑制必要转弯。
- 安全避障过滤器在二维环境使用相同规则，并把执行动作反馈到下一步观测。
- “关闭安全过滤”的消融只在评测时进行，固定同一模型，明确这是部署保护效果评价。

调试时分别记录每项奖励累计值，检查是否出现原地不动、只直行、绕圈或贴墙。

### 6.5 PPO 起始配置

| 参数 | 起始值 |
|---|---|
| 策略 | MLP，隐藏层 128、128 |
| 环境数 | 在 1、2、4 中按吞吐量实测选择 |
| n_steps | 每环境 512 |
| batch_size | 256，保证可整除有效 rollout |
| n_epochs | 10 |
| learning_rate | 3e-4 |
| gamma / gae_lambda | 0.99 / 0.95 |
| clip_range / ent_coef | 0.2 / 0.01 |
| 调试预算 | 先完成 1 万步全流程 |
| 正式预算 | 每种子先 30 万步，再按验证结果决定是否增加 |
| 训练种子 | 3 个，保存实际值 |

- 每 2 万步在固定验证任务上评估，使用确定性动作。
- 以验证成功率和碰撞情况选择检查点；正式测试集只在冻结模型后使用。
- 记录训练奖励、验证成功率、回合长度和碰撞率，不能只展示一条奖励曲线。
- 32 格先跑通流程；是否升级到 48 格由验证表现和吞吐量决定。
- 连续动作作为主方案；离散动作是独立配置，需重新训练和记录，不能混为一组实验。
- 同一随机种子在 Windows 和 Linux 上不保证完全相同的训练轨迹，比较时看评估指标。

### 6.6 吞吐量测量

先跑 1 万步，分别测试 1、2、4 个环境：

- 总墙钟时间
- 环境采样速度
- PPO 更新耗时
- CPU 利用率和内存

选择实际最快且稳定的组合，不要每个环境都开满线程。训练时间按 `T × N / 10000` 估算，不预设固定分钟数。

### 6.7 模型导出与跨系统部署

模型包至少包含：

```text
models/<model_id>/
├── ppo_xxx.zip
├── vecnormalize.pkl       # 若使用 VecNormalize
├── obs_spec.yaml          # BEV、目标、运动状态定义
├── train_config.yaml      # PPO、奖励、课程参数
├── train_meta.json        # 种子、步数、日期、版本、commit
└── validation.json        # 验证任务与结果
```

- 使用 `VecNormalize` 时保存统计量；部署加载后关闭统计更新（`vec.training = False`），并保持相同归一化。
- 虚拟机 Python 环境必须能同时导入 `rclpy` 和 SB3；使用 `--system-site-packages` 创建 venv。
- 部署测试顺序：模型加载 → 固定观测推理 → 空场景 → 单障碍 → 转角 → 完整路径 → 正式实验。
- 模型包附带哈希和规格版本；任一端修改观测定义后重新验证。

## 7. 安全机制

### 7.1 安全节点职责

安全节点约 20 Hz 输出，任何时候只接受当前模式的候选命令。检查：

- 候选速度是否有限、是否过期。
- 传感器是否有效。
- TF 与路径是否可用。
- 限幅、速率限制、避障过滤、急停锁存。

传感器或命令超过 0.5 秒无有效更新时停车。

时间处理：

- 消息年龄使用仿真时钟。
- 通信存活另用单调墙钟监测。
- 仿真暂停时不持续重放运动命令，恢复后等待新鲜数据。
- 低实时率不能一概当作通信故障。
- 真正中断、时钟跳变或重置时清空命令历史。

### 7.2 用足迹间隙与运动方向判断危险

先把雷达点转换到底盘坐标，依据实测足迹估计障碍间隙。

- 直行检测前方运动区域。
- 转向额外检查足迹旋转扫掠区域。
- 矩形足迹在障碍旁不能默认允许原地转向。

初始制动判据：

```text
required_clearance = safety_margin
                   + v × reaction_time
                   + v² / (2 × brake_deceleration)
```

- 反应时间包含观测年龄、推理和控制延迟。
- 制动减速度通过仿真运动测试确定。
- 该规则是工程近似，不构成绝对安全保证。
- 侧方障碍不应无条件阻止平行直行，但必须参与转向扫掠判断。

停车规则：

- 急停、无有效路径、无有效观测、候选命令超时 → `v=0, ω=0`。
- 前方过近时是否允许转向，必须经过足迹检查。
- 安全停车不能无条件保持角速度。

### 7.3 干预记录

- 首次从不干预进入减速/停车状态时记一次事件。
- 持续干预按持续时长累计，不每个控制周期计数。
- 使用迟滞和短暂恢复窗口减少阈值抖动重复计数。
- 记录原因、开始/结束时间、原始动作和执行动作。
- 人工急停单独统计。
- 正常实验不得用人工遥控帮助 PPO 完成任务；发生人工介入则标记为介入或失败，不能计入自主成功。

### 7.4 安全测试

- 停止策略节点。
- 停止雷达。
- 发送非有限速度。
- 切换模式。
- 急停锁存与复位。
- 雷达过近、前方障碍、侧方障碍、转弯扫掠。
- 每次都应得到预期停车或限速行为。

## 8. 可复现实验

### 8.1 主要对照实验

| 实验组 | 决策方式 | 避障安全过滤 | 正式运行数 |
|---|---|---|---|
| A | Nav2 全局规划 + DWB | 开启 | 24 |
| B | 同源全局规划 + BEV PPO | 开启 | 24 |
| C | 与 B 相同模型 | 关闭额外避障过滤，仅仿真 | 12，消融 |

- A、B 各使用 2 个场景 × 4 组起终点 × 3 次重复，共 48 次。
- 起终点覆盖直达、绕障、窄通道、多转弯；实际路径长度在场景中测定。
- 三次重复是重复运行，不是三个独立训练种子。
- 三个训练种子的稳定性在二维固定测试任务中分别报告。
- 主 Gazebo 实验使用验证集预先选定的一个模型，注明模型和训练种子，不在测试集上挑最好模型。
- C 选每场景 2 个代表任务，每任务 3 次，共 12 次，复用 B 的配对结果。
- C 保留速度上限、超时停车、唯一输出和人工急停，只关闭额外障碍减速/拦截逻辑；碰撞检测和独立评测始终开启。
- 至少一个测试布局未参与训练和调参；如果用它调试部署，另设最终保留布局。

### 8.2 对照条件

- 同一机器人足迹、地图、定位、全局规划配置、速度上限、侧向速度约束、仿真参数、外部安全模块。
- 两种方法允许在验证任务上合理调参，预先约定相近预算，冻结后不针对测试任务修改。
- 若 Nav2 保留标准恢复行为，明确主实验比较的是完整导航系统；不能把差异全部归因于局部策略。
- 若要单独比较局部控制器，需进一步统一任务管理和恢复逻辑，作为另一项实验。

### 8.3 每次运行的重置流程

1. 切换 `stop`，取消任务，连续输出零速度。
2. 将 Gazebo 机器人实体移动到规定起点，清除线速度和角速度；同时恢复环境障碍状态。优先使用带固定出生位姿的重新启动方式。
3. 若使用实体状态服务，先检查服务和插件存在并验证行为；**只设置 `/initialpose` 不会移动 Gazebo 实体**。
4. 检查里程计参考、TF、仿真时钟是否因重置改变；清空旧路径、观测缓存、上次动作、控制器和安全节点历史。AMCL 初始位姿使用规定起点。
5. 等待激光、odom、TF 新鲜有效，并检查 AMCL 位置/方向误差或协方差满足门槛；不只固定等待 2 秒。
6. 记录实际出生位姿和速度；超出容差则重置失败，不开始计分。
7. 启动记录，发送同一目标，按统一起止事件计时；成功、碰撞、超时、卡死或节点故障后停车并保存数据。

建议出生容差：位置 0.02 m、角度 0.02 rad。服务式重置难以清理状态时，直接完整重启。

### 8.4 统一评测指标

独立 `evaluation_node` 对两种方法使用相同标准；Nav2 和 PPO 自身的成功信号只作诊断。

| 指标 | 统一口径 |
|---|---|
| 成功率 | 进入目标 0.3 m 并保持 1 秒，全程无碰撞、无人工辅助 |
| 实际碰撞率 | Gazebo 碰撞体与障碍物接触；排除地面和机器人内部接触 |
| 完成时间 | 统一目标发送到成功，使用仿真时间 |
| 路径长度 | 积分仿真真值平面轨迹；滤除重置跳变并固定采样 |
| 最小间隙 | 足迹到障碍外表面的距离；激光估计与几何真值分开命名 |
| 安全干预 | 次数、总时长、原因分布 |
| 控制平滑度 | 执行速度的一阶变化，按实际时间间隔归一化 |
| 系统性能 | BEV/推理延迟、控制周期、实时率、墙钟耗时 |

- Gazebo 接触检测需先验证碰撞体和传感器有效，用可控碰撞测试。
- 若无法可靠读取接触，使用经过验证的足迹几何相交判据并明确口径；不能把雷达读数小于 0.26 m 直接记为实际碰撞。
- 仿真真值只供评测，不输入导航策略。

失败原因至少区分：

`collision`、`timeout`、`stuck`、`planning_failed`、`localization_error`、`sensor_timeout`、`node_error`、`manual_intervention`。

每次运行按预定优先级保留一个主要结束原因，可附多个诊断标签。

### 8.5 数据与统计

CSV 字段：

```text
run_id, pair_id, method, model_id, train_seed, repeat_id,
world, layout_id, start_id, goal_id, config_hash, code_commit,
success, collision, failure_reason, sim_time, wall_time,
```

- 保存任务清单中的精确起终点和布局种子。
- A、B 按任务配对并交替运行，避免所有 A 完成后再跑所有 B 导致配置漂移。

### 10.9 常见问题

| 现象 | 检查 | 处理 |
|---|---|---|
| `ros2: command not found` | 当前终端没 source | `source ~/.bashrc` 或新开终端 |
| `ros2 topic list` 为空但节点在跑 | ROS daemon 环境不一致 | `ros2 daemon stop` 后重试 |
| 不同终端互相看不到节点 | `ROS_LOCALHOST_ONLY` 不一致 | 所有终端都不设置，或全部设成相同值 |
| `map_saver` 报 `Failed to spin map subscription` | `/map` 无发布者或环境不一致 | 保持 SLAM 运行，统一 DDS 环境，确认 `/map` |

| TF 报 extrapolation | `use_sim_time` 不一致 | 所有节点统一 true |
| 地图保存失败 | 目录权限或没有地图 | 换到用户目录，先确认 `/map` |

本机经验：不要在不同终端里一个设 `ROS_LOCALHOST_ONLY=1`、另一个不设，否则节点会互相发现不了。

## 12. 风险与处理顺序

| 风险或现象 | 优先检查 | 处理方式 |
|---|---|---|
| 训练很好，Gazebo 不动或碰撞 | 观测排序、TF、归一化、动作执行 | 回放固定样例，再查运动模型和延迟 |
| Gazebo 太慢 | 实时率、图形负载、传感器开销 | 无界面评测、合理分配资源，参数冻结 |
| PPO 不愿转向或原地停留 | 分项奖励、不可达任务、动作缩放 | 三类小任务定位后再加训练步数 |
| 靠墙误停车 | 足迹、前方区域、转向扫掠 | 调整几何判据，两种方法共用 |
| RL 没有路径 | Action 状态、生命周期、代价地图 | 确认主动规划请求和有效返回，失败停车 |
| 起点不一致 | 出生位置、速度、AMCL、缓存 | 优先完整重启，不只发 initialpose |
| 安全模块掩盖策略不足 | 原始动作与执行动作差异 | 报告干预时长，做固定模型消融 |
| 跨系统依赖失败 | wheel、Python、ROS 包可见性 | 最小环境验收，必要时回虚拟机训练 |
| 工期落后 | 是否已有学习闭环 | 先取消拓展、动态场景，保留 AI 闭环和真实数据 |

不要用不断增加 PPO 步数替代接口排错。正式训练前未通过观测一致性或运动验证，暂停扩大训练规模。

## 14. 报告与结题材料措辞

### 14.1 人员与计算条件

> 小组具备一台 i7-14700 主机（64 GB 内存）。Windows 侧使用 Python 3.10 完成强化学习训练，VMware 侧分配 8 vCPU / 24–32 GB 内存搭建 Ubuntu 22.04 + ROS 2 Humble 仿真环境，用于 SLAM、Nav2 与策略闭环验证。训练环境为纯 Python 二维仿真，不依赖 ROS；训练完成的模型以文件形式迁移至虚拟机加载。训练采用轻量 BEV（48×48）与小型 MLP 策略，代码保持 `device` 可切换；如需扩大训练规模可迁移至 A6000 服务器，无需修改实现。

### 14.2 主要风险补充

> 本地计算资源有限，训练采用降采样 BEV、轻量策略网络和课程式场景递进控制成本；Gazebo 仅用于闭环验证与对比实验，不参与训练迭代。若训练收敛不理想，进一步降低 BEV 分辨率或改用离散动作空间。

### 14.3 技术路线补充

> 训练阶段使用与 ROS 节点同规格的 BEV 生成逻辑，在纯 Python 二维环境中完成 PPO 训练；部署阶段将策略接入 Gazebo ROS 2 闭环，通过统一配置文件、固定观测样例和跨系统推理测试保证观测与动作定义一致。

### 14.4 预期成果措辞

把“训练大规模模型”改为“完成可复现的 CPU 训练流程与策略模型”，强调流程完整、结果可复现，而不是模型规模。
